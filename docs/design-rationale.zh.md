# 设计原理

本文档解释 facetta **为什么**这样设计——那些决策、迫使我们做出这些决策的约束,
以及有意接受的取舍。关于实现**如何**工作,见 [architecture.zh.md](architecture.zh.md);
关于这个库**做什么**以及如何使用,见 [README](../README.md)。

## 镜像,而非数据库

facetta 是一个进程内的只读查询加速层。外部主库是唯一事实源;facetta 不拥有
任何数据,随时可以从主库完整重建。

这一个决策就消除了存储系统最难的那些问题:没有 WAL,没有崩溃恢复语义,没有
跨实例复制(每个实例独立同步),持久化只是重启加速器——快照加载失败就回退到
全量拉取,绝不允许阻塞启动。下文的一切都依赖于此:每当某个机制需要引入复杂度
才能*独立保证正确*时,设计选择转而接受一个有界的偏离窗口,让基于事实源的重建
把它收敛回来。

## 为什么用字典编码的列式存储

驱动性负载是高 QPS 请求路径上对一张表的查询,这张表由低基数字符串维度和数值
指标组成,查询形态固定:等值过滤,按组取并集,指标求和。朴素布局(每行一个堆
对象、每字段一个字符串、以 map 组织、线性扫描)在行数增长到百万级时会同时在
三个方面失败:常驻内存膨胀,GC 标记开销随对象数线性上升,O(N) 扫描耗尽请求
路径上的 CPU。

字典编码加列式布局用一个结构同时解决这三个问题:维度字符串变成稠密的 `uint32`
id,数据区因此完全不含指针——GC 需要扫描的对象数只取决于字典基数(几万),
而不是行数(几百万)。行按打包的索引键排序,使等值前缀查询变成两次二分查找
而非一次扫描。500 万行时整张表约占 ~290 MB,堆对象约 ~32k 个。

## 为什么用不可变快照 + 单个原子指针

读者加载一次 `atomic.Pointer`,随后操作的世界绝不会在脚下改变。这就是读路径
的全部并发模型:没有锁,没有 epoch,没有引用计数,没有 hazard pointer。旧视图
在飞行中的查询释放后被直接垃圾回收。

接受的代价是:每次变更都发布一个完整的新视图,重建期间会短暂持有表的两份副本
(压实期间约 ~2× 内存峰值)。对这种负载而言这个取舍是正确的,因为读的数量比写
高出几个数量级,而量化目标要求读*永不*被写阻塞。

一个被有意否决的替代方案:共享前缀的追加式 delta 可以把 `Apply` 从 O(delta)
降到 O(batch),但它以一个微妙的"读者只见前缀"的内存模型契约破坏了"已发布视图
完全不可变"这一不变量。经过实测的修复方案(克隆元组索引 map 而非重新编码;
按维度惰性克隆 `extras` 字典)在保住不变量的同时消除了平方级的分配开销,于是
剩下的每次 `Apply` O(DeltaRows) 列拷贝被接受、写入文档,并由 compactor 策略
约束上界——宿主应当批量提交记录,而不是逐条调用 `Apply`。

## 为什么库边界是"纯存储 + 压实策略"

早先的一版有一个 `Syncer`,它负责摄入、增量拉取位点、对账节奏和启动时
"加载或回退"的编排,还要求用户实现一个 `Source` 接口。这些全都属于宿主的集成
契约——它们因部署而异,与一个读优化的聚合表毫无关系。库边界被收缩为 Store
原语(`Apply` / `ReplaceAll` / `Compact` / 快照保存与加载 / `SyncPosition` /
`Stats` / `NeedsCompaction`)加上一个可选的后台 `Compactor`,后者只决定*何时*
压实,对数据从哪里来一无所知。

在这个边界之内,机制与策略同样保持分离:delta 的绝对上限(`MaxDeltaRows`)
放在 Compactor 里,而不是 `NeedsCompaction` 里,因为后者回答的是一个状态问题
("压实会不会改变视图?"),而这个上限是一个延迟策略旋钮。

## 没有删除事件的淘汰

上游同步流只携带 upsert——没有删除通知。设计没有要求上游提供删除事件,而是
通过收敛来保证一致性,分三层:

1. **全局 TTL**:重建时丢弃 `UpdatedAt` 落出保留窗口的行。
2. **记录级墓碑**:写入一条 `ExpireAt <= now` 的记录,该行立即不可见,并在下次
   压实时被物理回收。
3. **宿主驱动的 `ReplaceAll`**:周期性或按需地从主库全量重建,是唯一能收敛
   *一切*的路径,包括绕过墓碑的上游硬删除。

有一个边界情况是被有意定义而非防止的:物理回收会遗忘元组的 `UpdatedAt` 水位,
因此之后乱序到达的**更旧**记录会使该行复活。永远记住每一个已回收的墓碑会让
内存无界增长;这种复活恰好落在 `ReplaceAll` 所修复的漂移类别里,所以参考
oracle 对它建了模,库也把它写进文档,而不是与之对抗。

出于同样的原因,`SyncPosition`(宿主的增量续传游标)在压实回收掉最新的行时
允许回退:从回退后的位点重新拉取只会重新摄入已过期的记录,它们保持不可见并
再次被丢弃——无害,因此不为防止它花费额外的簿记开销。

## 记录级 TTL:读时可见性,重建时回收

`Record.ExpireAt` 必须同时满足两个时钟:用户希望过期*立即*生效(Redis 风格),
而物理回收只有在重建时才廉价。于是可见性与回收被拆开:查询对 `now` 采样一次
(结果内部一致)并跳过已过期的行——每个候选行只需一次 `int64` 比较,且对不含
过期行的视图完全跳过——而压实在之后物理删除它们。

一条微妙的顺序规则保证引擎与 oracle 逐位相等:已经过期的记录仍然经由正常的
upsert/去重路径被*存储*,再由读时检查隐藏,而不是在摄入时丢弃。去重必须看到
它们——一条较新但已过期的记录仍须遮蔽一条较旧且不过期的重复记录——所以
"先存储、读时过滤"是唯一符合参考语义的顺序。

这个特性所要求的快照格式升级(v2 增加了过期列)确立了持久化策略:**不做向后
读取兼容**。版本不匹配的文件被拒绝,宿主回退到全量拉取——快照只是缓存,回退
路径本来就必须存在且可靠,格式迁移代码只会是没有收益的复杂度(KISS)。

## 有界查询延迟:快速拒绝而非排队

受截止时间约束的调用方认为,一个慢答案比一次即时拒绝更糟。最坏情况过去是无界
的:退化的全表扫描是 O(N)(3000 万行约 ~174 ms),而按比例触发的 delta 只约束
它的*相对*大小。

修复利用了一个结构性性质:在规划完成之后、触及任何行之前,一次查询的总工作量
已经确定——合并后的基底候选区间加上 delta 行数。`Config.MaxScanRows` 把它变成
一次快速拒绝式的预算检查,使用与真实扫描完全相同的算术(重叠区间只计一次),
复杂度 O(#intervals) 且无分配,在访问任何行之前完成。`CompactorConfig.MaxDeltaRows`
则从绝对量上为 delta 的无条件线性扫描封顶,与之互补。

有两个细节是有意为之:

- `ErrScanBudget` 是一个裸哨兵错误,从不被包装——`fmt.Errorf` 会分配,而拒绝
  路径必须保持零分配。需要具体数字的调用方去读 `Stats()`。
- 保证的是**工作量**(访问的行数),不是墙钟时间:GC 与调度器抖动叠加在其上。
  诚实的契约是"这次查询最多触及 K 行";调用方对 `ErrScanBudget` 的反应应当是
  回退(到主库或降级答案),而不是重试。

预算拒绝是一个可用性特性,不是语义变化:oracle 没有预算概念,等价性测试在
禁用预算的情况下运行。

## 聚合、IN 与 GROUP BY:在不解冻契约的前提下扩展

原始的查询形态(等值过滤、对每个指标求和)是一份冻结契约——它的语义、零分配
保证和实测延迟必须在之后的每一个特性下存活。更丰富的查询形式是在这一约束之下
加入的,由此产生四个决策:

- **新能力,新入口。** `QueryAggs` 和 `QueryGroupBy` 是共享同一个规划器的独立
  方法,而不是 `QueryGroups` 上的选项——一个 options 结构会把分支和更大的
  scratch 放到冻结路径上。对既有接口面的唯一新增 `Cond.In`,被刻意工程化到让
  不含 IN 的查询付出的代价无法测出:它解析出的 id 存放在按查询一份的池里,
  没有 IN 时以 nil 指针传递(按 plan 一份的数组会让每次查询都要清零初始化的
  栈 scratch 膨胀十倍);成员检查也被留在行匹配器之外,因为哪怕对它的一次调用
  都会把匹配器推出编译器的内联预算——两种变体都实测出两位数百分比的退化,
  被否决。
- **NaN 就是空聚合。** 对零个匹配行做 Min/Max/Avg 返回 NaN——float64 中
  SQL NULL 的替身。任何数值哨兵(0、±Inf)都是合法的数据值;额外加一个"有效"
  标志则会改变输出形态。oracle 产出同样的 NaN,等价性测试以 NaN 感知的方式
  比较。
- **IN 最初只过滤,后来被重新审视。** 当时区间簿记的顾虑是真实的:一个按展开
  定尺寸的按 plan 一份数组,不管有没有查询真的用到展开,都会让每次查询的
  scratch 膨胀。这个限制一直保留到查询形态限制本身被解除为止(见下文"解除
  查询形态限制")——一旦 scratch 从一份固定的按 plan 数组换成按输入定尺寸的
  栈/池数组,索引前缀维度上的 IN 条件就能展开成候选区间,而不必让纯等值路径
  付出代价,这条曾经推荐的"每个值一个组"变通做法也就不再必要。
- **Distinct 计数走精确,不走 sketch。** `COUNT(DISTINCT dim)` 通常是引擎搬出
  HyperLogLog、拿误差界换内存的地方。但这里字典编码已经把值空间收敛掉了:
  一个维度的 distinct 集合本身就是其 id 上的一张位图,尺寸在查询开始时即已知
  (base+extras 合并基数)且很小(3 万个值约 4 KB)。精确的代价是每个 distinct
  列一次分配、每行一次测试并置位(test-and-set)——近似方案合并起来反而更慢,
  严格更差。GROUP BY 中的按组 distinct 则改用一个 seen 三元组集合去重,其文档化
  的成本随唯一 (组, 值) 对的数量增长——最坏 O(匹配行数),明说而非隐藏。
- **整数维:身份就是 int64 值,靠规范化编码强制。** 对字符串拼写的数字做范围
  谓词,最初上线时带着人格分裂——身份看拼写、范围看解析值——并在评审中被
  否决:`"1"` 和 `"1.0"` 是两个不同的行、却被同一个范围重复计数,这是错的。
  修法不是类型化列(每行 8 字节,而且索引打包仍然需要字典),而是规范编码:
  每个写入边界都把整数维的值改写为纯十进制形式(非整数输入直接拒绝,与 arity
  不匹配被拒绝是同一种方式),每个查询边界都对条件值做规范化——经由栈上渲染
  的键,零分配——于是相等、IN、范围、去重和 group-by 键全都对同一个整数达成
  一致。特意选 int64 而非 float64:维度身份要求精确,而 float 身份在 2^53 之上
  有一道静默的精度悬崖,不同的值(纳秒级时间戳、大 ID)会坍缩成同一个——外加
  NaN/±Inf/负零这些整数根本没有的边角情况。小数桶遵循与精确指标相同的纪律:
  放大为最小单位。保序字典被否决,因为压实的重编号必须相对旧 id 单调(按值
  排序会迫使每次压实做一次全量重排);每查询扫一遍字典被否决,因为那意味着
  每次调用毫秒级的解析。取而代之,整数维字典直接以 int64 值本身
  为键、完全不存字符串——身份由 map 键强制,拼写仅在输出边界(group-by 键、
  快照保存)按需渲染——其 `vals []int64` 列让一次范围检查只是每行两次整数
  比较。时间支持靠编码约定
  (unix 时间戳),而非解析时间格式。类型住在维度声明自身上(`Dim{Name, Type}`
  ——每个维度一个结构体,而非平行标签表,未来的 `DimFloat` 会是加法式扩展)。
  `DimType` 不进 schema 指纹;加载时改为校验规范性,因此在声明之前写出的快照
  会被拒绝,进入常规的回退全量拉取。
- **GROUP BY 放宽了分配规则——显式地,且仅在此处。** Group-by 的输出天然是
  可变大小的,"零分配"不可企及;诚实的契约是每次调用 O(结果组数) 的分配
  (map 键驻留、排序 scratch),绝不是 O(扫描行数),并在复用的 `GroupedResult`
  上摊销。选择对打包 id 元组做哈希聚合,而不是流式的按排序序变体,是因为
  delta 覆盖层本来就无序——一条永远可用的代码路径,胜过其中一条只在部分情况
  适用的两条路径。输出按键字符串排序,结果因而确定;键直接别名不可变字典,
  而非复制。

## 解除查询形态限制

最初的固定按 plan 数组(16 组、每组若干条件等等)对请求路径的真实形态而言尺寸
本就宽裕,但它们同时也是调用方可见的天花板:调用方的过滤列表一旦超出数组尺寸,
得到的是硬错误而不是变慢的答案——这对一个整个卖点就是"形态合适时快、不合适时
安全"的库而言是错误的取舍。`Config.MaxScanRows` 已经存在,把"变慢"变成一个
有界、可拒绝的代价,按形态设的静默硬上限只是把这份职责做得更差地重做一遍。
于是每一个形态限制——组数、条件数、IN 条件数与值数、range 数、聚合列数——都被
解除,`MaxScanRows` 成为留下的唯一调用方侧护栏。

在不放弃零分配热路径的前提下解除限制,意味着把按查询一份的 scratch 从一个
固定数组拆成两个来源。一个落在栈容量之内的形态(`scratchBack`,按数组过去
被固定的那些相同常量定尺寸)完全跑在调用方自己的栈帧上,`queryScratch` 指针
永不逃逸;更大的形态则从 `sync.Pool` 借一份 scratch,按形态自身的*输入*计数
(组数、条件数、已解析的 IN 值数等等)精确定尺寸,而不是按表内容——所以同一个
查询形态无论当前匹配了多少数据,路由方式始终一致。路由因而是调用的纯函数,而
不是世界状态的函数,这让它易于推理也易于测试。归还时保留容量超过 1MB 的池化
scratch 会被丢弃而不是放回池——一个病态形态应当只代价一次超大分配,而不是
为之后随便哪个恰好抽中同一个池槽位的无关查询钉住一大块内存。

两个后续优化在同一份预算之内就把自己的成本挣了回来。第一,每个 IN 条件的
候选窗口在规划时排序一次;匹配一行对一个不超过 16 个 id 的小窗口仍然线性扫描
(在这个尺寸上,带分支的线性扫描在真实硬件上胜过二分查找的指针追逐),但更大的
窗口改用二分查找,把逐行成员判断从 O(n) 变成 O(log n)。第二,前导索引维度上的
IN 条件现在会加入索引前缀规划,而不再只是事后过滤行:规划器把它展开成每个已
解析 id 一条候选键区间——若干个索引前缀维度各自带 IN 时就是跨维度的笛卡尔积——
由一个跑遍已覆盖前缀的里程表(odometer)遍历生成。展开是有预算的,不是无条件
的:只有当组合数乘以 ⌈log₂ 行数⌉ 仍低于全表扫描的行数时,才值得把前缀再扩展
一个 IN 维度。这个交叉点是一个乐观的成本*模型*,不是硬限制——它假设每个候选值
和每一行的成本均匀,单靠它自己也说明不了一个查询在这套模型的簿记本身变得昂贵
之前,到底可以探测多少候选值。真正约束最坏情况规划开销的是一个硬性容量:
池化 scratch 在自己"每组一个"的底线之上,为展开预留固定的 4096 个区间额度,
一旦需要的槽位超过这个数,不管成本模型估算出什么,展开就直接停下——像未覆盖
前缀过去一直做的那样,退化为普通扫描。

多个组各自带索引维 IN 的查询,暴露了栈路径上同一种稀缺性的一个更窄版本,
栈路径的区间预算本就刻意小得多:较早的一个组的展开可能吃掉其中大部分,把
较晚的组降级为全表扫描,顺带浪费掉较早那个组自己的展开——并集扫描最终会
访问接近整张表的行数,无论第一个组的 IN 选择性有多高。与其为了更精确地路由
去重新推导规划器自己的组合数簿记,路由检查改为过度估计:把每个组自己的最坏情况
区间需求估计为该组所有 IN 条件输入值数量的*乘积*(规划器的展开是该组已覆盖维度上
的笛卡尔积,不是求和),再把这个估计值按组求和,总数一旦超过栈的整个区间预算就
路由到池——池那份大得多的额度能从容满足它。这个检查更早的一版直接对每个 IN
条件的值数量求和,而不是按组取乘积,这会低估需求:一个组带两个 3 值和 4 值的
索引维 IN,最多需要 3×4=12 个槽位,而不是 3+4=7 个,于是一个带着这个组、外加
第二个 6 值 IN 组的形态,按(2 组 + 13 个求和值)读作 15,低于 16 槽位的预算,
留在了栈上——在那里恰好按上文描述的方式挨饿,这个问题在评审中被发现并修正为
按组取乘积。这个乘积估计仍然在两个安全的方向上过度估计(它只会把一个原本在栈上
也能跑的形态多路由到池一次,绝不会反过来漏判):它会把落在非索引维上的 IN 条件
也乘进去,因为路由检查本身跑在任何字典查找之前,尚且不知道哪些维是索引维;它
也会把第二个落在某个维度上、而该维度已经被第一个 IN 条件覆盖的 IN 条件重复计入,
而规划器实际上只会应用一次。在一个"两个组、各自 10 值 IN"的形态上实测,修正后
的检查比留在栈上挨饿快大约 2.9-3 倍;这份改路由对本不需要改路由的形态所增加的
一次池往返,相对那些查询自身的开销而言小到测不出来——现在也包括单个组里一个维度
上带 16 值 IN 的形态(需求恰好是 16,仍然落在栈预算之内,保持零分配)。

`Cond.Range` 有意没有跟着 IN 走上索引前缀路径。索引键是从字典 id 打包出来的,
而字典 id 是按首次出现顺序分配的,不是按值分配——两个 id 在数值上相邻,并不
说明它们对应的底层整数相邻。因此一个 range 条件无法像等值或 IN 匹配那样被
转换成按键排序基底上的一段连续切片;它保持为逐行过滤——两次整数比较,依然
零分配,和一直以来一样。

这项工作中反复出现、值得专门记一笔的一个 Go 实现约束是:逃逸分析把两种写法
无条件地判定为堆逃逸,没有任何通过重构、内联或把切片换成数组来证明其反面的
办法——不写下来,未来的"清理"很容易把它踩回去。第一,一个返回指针、且该指针
别名自身接收者某个字段的函数,会把接收者本身逼上堆,哪怕这个返回的指针从未
逃出调用方——必须改为*按值*返回,再由*调用方*在自己的栈帧里对这个本地值取地址。
第二,把一个真正的切片(底层是指针)存进某个字段,而这个字段所在的结构体本身
是一个被索引切片里的一个元素——`qs.plans[i].someSlice = x`,这里 `qs.plans`
本身就是切片——会让整条写入路径被标记为逃逸,不管存进去的切片是不是刚从池数据
重新切片出来、生命周期从不超出这次调用的那种。往同一个字段里存一个纯粹的
`(offset, count int32)` 值对则不会触发这一点;只有指针形状的值才会。这就是
为什么 `groupPlan`、`inWindow` 以及按查询一份 scratch 的其余部分,持有的是
指向共享池的偏移量+计数视图,而不是子切片——这不是风格偏好,而是唯一能让整个
按查询 scratch 在快速路径上留在栈上的写法。把这些偏移量+计数对换回
`[]int32`/`[]inWindow`/`[]rangeWindow` 字段,会悄无声息地把每一次查询——包括
那些从不涉及 IN 条件或展开的查询——都挪到堆上;`TestQueryZeroAlloc` 是能抓住
这一点的绊线,但 `queryScratch`(scratch.go)上的 CAUTION 注释存在的意义,就是
让后来者不必先自己踩一遍这个坑才明白过来。

## 按时间门控的字典压实

字典 id 一经发放,就被固化进行数据、旧视图和磁盘快照——无法原地回收。因此被
TTL 或墓碑淘汰的行会留下"幽灵词条",引发三个慢性问题:字典内存单调增长;
打包键的位宽按字典*长度*而非活跃基数计算,因而虚高;一旦索引维度的位宽之和
超过 64 位,`Compact` 将永久失败(`ErrKeyOverflow`),而 `Apply` 继续填充
delta——一个只有宿主 `ReplaceAll` 才能打破的死锁。

因此 `Compact` 在进程内回收字典:标记被存活行引用的 id,按维度对幸存者单调
重编号(单调 ⇒ 已排序的基底保持有序,归并仍是同一个线性 zip),并按活跃基数
重新计算键位宽。

重编号各遍的开销约占归并墙钟时间的 40–60%,这迫使我们回答*何时*运行它们。
先估算累积的垃圾量需要与回收它相同的标记遍——检测与治疗一样贵——所以门控
基于**时间**而非垃圾估算:`DictCompactInterval` 把垃圾约束在一个间隔内的
变更量之内,运维者纯粹按垃圾允许累积多久来选择间隔。有一个例外可以越过门控:
被 `ErrKeyOverflow` 拒绝的归并会立即带上字典压实重试,因为按垃圾虚高的字典
计算出的位宽在回收之后可能就放得下了。结果是:只要*活跃*基数在 64 位键预算
之内,存储总能在进程内自愈,无论门控与否。

## oracle 先行的测试

facetta 所取代的那个朴素模型——每行一个堆对象、以完整维度元组为键、线性
扫描——被保留在仓库里,即 `reference_test.go`,它是**唯一的语义权威**。任何
对引擎语义的改动必须先改 oracle;`TestEquivalenceRandomized` 用完全相同的
随机化负载驱动两侧(乱序时间戳、三态过期、混合的 apply/compact/replace、
运行中推进的注入共享时钟),并断言每一次查询完全一致。

这反转了重度优化引擎的常见风险:正确性由约 150 行显然正确的代码定义,数千行
列式机制只需要与它保持一致。在 oracle 之外,绊线测试钉死非功能性保证,使其
无法悄然退化:`TestQueryZeroAlloc`(热路径零堆分配)、`TestCapacity5M`
(500 万行下的内存/延迟红线)、`TestQueryLatencyDuringCompact`(读永不被写
阻塞)。

## 量化红线

设计目标是固定的数字,由基准测试固化而非愿景口号:500 万行常驻内存
≤ ~400 MB;典型索引查询 ≤ 5 µs 且 0 分配;压实 < 2 s;读永不被写阻塞。
README 的基准表只允许填实测值;任何热路径改动都要重跑性能层并更新该表。

## 指标精度

指标聚合就是一个顺序的 `float64` 求和。整数值指标(计数、以最小单位计的金额)
在 2^53 以内是精确的——在任何现实规模下都逐位精确。小数指标在末尾比特上依赖
求和顺序,因为压实会物理重排行。引擎不做补偿(Kahan 求和等);如果某个指标
必须精确——典型如金额——宿主应将其存储为最小单位的整数计数。这让热循环保持
平凡,精确性规则也易于表述。
